# 部署配置系统说明

> 状态：已从“目标设计方案”收敛为“当前实现对照说明”。

这份文档不再描述一个尚未完全落地的统一部署平台，而是说明当前仓库里的部署配置系统实际到了什么程度、该怎么看、哪些部分仍属于半成品。

## 当前实现范围

仓库中确实存在一套部署配置资源，主要位于：

```text
deployment/
├── configs/
├── scripts/
├── schemas/
├── docs/
└── production/
```

它当前能表达的能力主要是：

1. 提供若干部署预设和模板
2. 提供配置生成、校验、部署辅助脚本
3. 提供 Ubuntu / 生产风格部署资源
4. 提供容器化生产风格编排文件

## 当前更准确的系统理解

应把它理解为：

- 一组部署配置资源
- 一组辅助脚本
- 一批预设和模板

而不是：

- 唯一权威部署入口
- 已经完全统一的多场景发布平台
- 所有部署模式均已严格对齐的配置中心

## 当前可识别的三条部署路径

### 1. 本地开发联调

主要参考：

- 根目录 `start-system.sh`
- 根目录 `docker-compose.yml`

特点：

- 本地前后端 + Docker 基础设施混合
- 更偏开发验证

### 2. Ubuntu / 本机服务化部署

主要参考：

- `deployment/scripts/start-ubuntu-services.sh`
- `deployment/docs/ubuntu-amd-deployment.md`
- `production/*.service`

特点：

- 更接近生产
- 常依赖外部或独立运行的 LLM / Embedding / Reranking 服务

### 3. 容器化生产风格部署

主要参考：

- `deployment/production/docker-compose.prod.yml`

特点：

- 主后端、AI 服务、Redis、Nginx、监控容器化

## 当前目录中真正有参考价值的部分

### `configs/`

作用：

- 保存预设、模板和用户配置

现状：

- 对理解部署意图有帮助
- 不能替代对真实启动脚本和生产配置的核对

### `scripts/`

作用：

- 配置生成、校验、修复、启动辅助

现状：

- 部分脚本可用
- 不能默认认为脚本之间已经构成完整闭环

### `production/`

作用：

- 更接近可执行的生产部署资源

现状：

- 是当前最值得对照的生产风格资料之一

## 本文档已去掉的失效内容

本次去掉了以下不再适合作为当前事实的内容：

1. 大量未来式设计目标
2. 未与仓库现状对齐的统一配置格式示例
3. 把 AWS、Docker、本地 GPU 全部写成已完全统一的实现
4. 把部署配置系统写成已经闭环的发布平台

## 当前维护建议

后续如果继续整理部署文档，建议按以下顺序：

1. 统一变量名
2. 统一开发态与生产态端口基线
3. 统一脚本入口优先级
4. 再决定是否继续扩展 deployment 配置框架
