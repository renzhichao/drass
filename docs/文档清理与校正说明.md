# 文档清理与校正说明

本文档用于回答两个问题：

1. 当前仓库里哪些文档需要清理、归档或降级为历史资料。
2. 这轮整理之后，哪些文档应作为“正确项目”的优先入口。

## 清理判断原则

以下任一情况成立，就应进入清理清单：

1. 文档把项目仍描述为 Dify 配置工程，但仓库实际上已经是多服务系统。
2. 文档引用了不存在或不再推荐的脚本。
3. 文档使用了已经失效的默认端口或服务关系。
4. 文档只是需求草案，但容易被误认为当前事实。
5. 文档与现有部署脚本、生产配置、服务代码相冲突。

## 当前已完成第七轮复查结论

这一轮最终只保留文档层整理，没有继续落地脚本或代码修改。

本轮确认出的剩余问题主要集中在运行辅助脚本，而不是主入口文档：

| 类型 | 典型位置 | 当前结论 |
| --- | --- | --- |
| 环境专用修复脚本 | `deployment/scripts/fix-*.sh` | 仍带明显宿主机假设，不应当作标准入口 |
| 环境专用诊断脚本 | `deployment/scripts/check-*.sh`、`debug-*.sh` | 仅适合排障，不适合做正式部署规范 |
| 一次性初始化脚本 | `setup-venv.sh`、`install-*.sh` | 仍有目录和用户假设，后续若继续治理应单独收敛 |
| 特定 GPU / 模型启动脚本 | `restart-vllm-optimized.sh` 等 | 仍属于特定机器运维脚本，不应扩散成项目基线 |

## 当前不建议继续扩散为“主入口”的脚本类型

除了文档之外，仓库里还有一类需要明确降级认知的对象：环境专用辅助脚本。

这些文件未必都错误，但不应继续当作“标准项目入口”传播：

| 文件类型 | 典型位置 | 当前建议 |
| --- | --- | --- |
| 单机 Ubuntu 修复脚本 | `deployment/scripts/fix-*.sh` | 仅作排障参考，不作主入口 |
| 单机诊断脚本 | `deployment/scripts/check-*.sh`、`debug-*.sh` | 仅作诊断工具，不作部署规范 |
| 一次性环境初始化脚本 | `deployment/scripts/install-*.sh`、`setup-venv.sh` | 仅在明确环境前提下使用 |
| 特定 GPU / 模型目录脚本 | `restart-vllm-optimized.sh` 等 | 仅用于匹配的宿主机环境 |

它们的共同问题通常是：

1. 写死项目目录或用户名。
2. 混入临时排障逻辑。
3. 把环境现场假设写进脚本本体。
4. 容易被误抄为项目级标准入口。

## 当前已经识别出的失效信息类型

### 1. 失效项目定位

典型问题：

- 把项目写成 Dify 配置管理系统
- 忽略前端、主后端、文档处理、重排、生产部署链路

### 2. 失效启动脚本

典型问题：

- `start-simple.sh`
- `start-langchain.sh`
- `start-full-langchain.sh`

这些名称在旧文档里出现过，但不应继续作为当前入口。

### 3. 失效端口基线

典型问题：

- 仍把 `3000` / `8080` 当作当前主链路默认端口
- 把所有环境都写成 `8000`
- 忽略生产风格 `8888`

### 4. 失效服务关系

典型问题：

- 把 `scheduler` 写成当前主链路关键服务
- 把 Dify API 地址当作系统当前默认依赖
- 未区分开发态和生产态的 AI 服务端口
